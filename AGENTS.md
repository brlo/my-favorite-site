# Правила для агентов

## Всё запускается в докере

Приложение целиком работает внутри докер-контейнера `bibleox` (поднимается `docker compose up`). Репозиторий примонтирован в `/app` bind-mount'ом: правки файлов на хосте контейнер видит сразу, включая `tmp/` и новые скрипты. На хосте `bundle`/`bin/rails` не работают (нет гемов, rmagick не собирается) — **не пытаться ставить их локально**, любую команду (`runner`, тесты, рейк-таски, скрипты из `script/`) запускать в контейнере:

```
docker exec bibleox bash -lc 'cd /app && bin/rails test test/services/bible_linker_test.rb'
docker exec bibleox bash -lc 'cd /app && bin/rails runner script/translations/bible/fix_brackets.rb'
```

Для тестов и `runner` нужны контейнеры `bibpostgres` и `bibredis`. Если они остановлены: `docker compose up -d postgres redis` и подождать несколько секунд.

Hot-reload подхватывает только `app/`, но не инициализаторы и бандл: после правок `config/initializers/*.rb` или `Gemfile` перезапускать контейнер (`docker restart bibleox`), иначе на каждом запросе 500 — например, новые методы `RedisConnectionPool` не видны коду запущенного сервера. После обновления гемов — полный прогон тестов и `bundle exec bundler-audit check --update`.

Dev-база — Postgres в контейнере `bibpostgres`, пользователь `bibleox`, база `bibleox_development`; читать можно напрямую:

```
docker exec bibpostgres psql -U bibleox bibleox_development -t -A -c "SELECT ..."
```

## Коммиты и PR

В сообщения коммитов и описания PR не добавлять упоминания об ИИ: никаких `Co-Authored-By: Claude`, `Generated with Claude Code` и т.п.

## Именование

Методы и переменные, возвращающие boolean, называем либо с префиксом `is_` (`is_something`), либо с окончанием `?` (`email_confirmed?`).

## Запуск кода и тесты

Тесты ходят в Redis по адресу из `config/settings.yml` (раздел `test`, база 15 в `bibredis`, с паролем как у development; образец в `config/settings.yml.example`). Если адрес пустой, клиент стучится на localhost:6379 и десятки тестов падают с `Redis::CannotConnectError`.

Тесты лежат в `test/` (minitest). Новую логику покрывать тестами рядом с существующими (`test/services`, `test/models`).

## Работа с контентом сайта — инструкции в docs/

Детальные рабочие инструкции вынесены в `docs/`; перед соответствующей работой прочитать нужный файл:

- `docs/translations.md` — перевод/правка статей, импорт YAML, обновление отдельной статьи на проде. Для китайского проекта дополнительно `docs/chinese-translations.md`.
- `docs/quotes-section.md` — перенос раздела «Библейские цитаты» на новый язык: инструменты, механика `q_build`, подводные камни Библий, заливка партии на прод.
- `docs/bibles.md` — добавление переводов Библии (MyBible-модули, регистрация, известные дефекты модулей).
- `docs/page-visits.md` — статистика посещений (`BotDetector`, счётчики в Redis, сводка `/admin`).

Правила, действующие всегда:

- Запись на прод (статьи, БД, импорты) — только по явному подтверждению с названной операцией, в том числе когда локально всё готово. Составную команду с записью на прод не склеивать с локальными шагами: при отказе не выполнится ничего. Не коммитить и не деплоить без команды.
- Греческие термины, обсуждаемые в статьях, писать по-гречески (ἄρτος, ἄζυма); русская транслитерация — только в русских статьях.
- Чужие незакоммиченные файлы в `db/translations/` (слепые сравнения других ИИ) не импортировать и не коммитить.

## llms.txt

`public/llms.txt` — описание сайта для ИИ-краулеров (стандарт llmstxt.org): схема адресов, переводы Библии, коды книг, разделы статей, языковые входы. Отдаётся статикой, как `robots.txt`, обновляется деплоем. Дополнять при появлении нового перевода Библии, нового языка статей (вход в Language versions + разделы этого языка) и при изменениях схемы адресов; новые ссылки проверять на живой странице.

## Прод и деплой

- Прод: `ssh bibleox`. Сайт: https://bibleox.com/
- Деплой: `bin/bib_deploy.sh`. На сервере он делает `git reset --hard origin/main`, поэтому сначала запушить в main. Алиасы `bib_*` лежат на сервере в `~/.bib_aliases.sh`, в репозитории их нет.
- Контейнер работает от uid 1000 / gid 1001. Если git на сервере запускается от root, файлы переходят к root, и `bundle install` падает с ошибкой записи в `Gemfile.lock`. Алиас `bib_update_code` сам возвращает владельца `1000:1001`; руками git на сервере лучше не гонять от root без `chown`.
- Корневые статические файлы (robots.txt, llms.txt, файл верификации яндекса) nginx отдаёт только по явным `location =` правилам — whitelist; всё остальное с расширением в корне режется `return 404`. Новый корневой файл требует правки `/etc/nginx/conf.d/bibleox.conf` на сервере (конфиг живёт только там, не в репозитории): добавить `location = /<файл> { root /projects/bibleox/public; }`, проверить `nginx -t`, перечитать `nginx -s reload`.
- Деплой может «не дождаться» сайта: при рестарте puma пре-компилирует ассеты дольше 15 попыток скрипта (~2.5 мин). Если `bib_deploy.sh` отдал fail с 502 — проверить логи (`ssh bibleox 'sudo docker logs --tail 50 bibleox'`) и статус сайта руками: часто приложение просто ещё поднимается.
- Статику (`/assets/...`) отдаёт отдельный хост `res.bibleox.com`
